黑客松方案 · 2026-10 · 基于 ZK-HADA / ZK-DAC v9.2

ShadowPass：给 AI Agent 的隐私预付卡

用 Face ID 给自己的任何 Agent 发一张隐私预付卡。卡有额度和用途限制，可以随时冻结，Agent 每一笔消费都瞒不了主人，而商家和钱包商都不知道这张卡属于谁。

  • 用户钱包 手机 PWA
  • Agent 钱包 MCP server，用户自己的电脑
  • 登录 Passkey + PRF
  • 收款 x402 自定义 scheme
  • 验证 链上 Groth16（Gate 合约）
  • 网络 Base Sepolia，Anvil 兜底
  • 名称 暂定，需查重

01产品叙事

我们要解决的问题，以及为什么现在值得做。

Agent 开始花钱了，但它的账本是公开的

2026 年，Agent 自主付款已经是主流产品形态。Coinbase Agentic Wallets（2026-02 上线）、Privy、Turnkey 都提供“给 Agent 一个钱包，加额度和白名单”的能力，x402 让 Agent 可以按次给 API 付费。

这些方案解决了“Agent 不碰私钥”的问题，却留下了两个隐私缺口：

  • 钱包商看得到一切。私钥在它的 TEE 或 MPC 里，策略引擎在它的服务器上，你授权了哪些 Agent、每一笔花在哪里，它都知道。
  • 商家和链上观察者看得到付款人。钱从你的账户地址付出，商家拿到地址就能把你在所有服务上的消费串起来。Agent 越勤快，你的画像越完整。

一句话定位

让用户很轻松地给自己的 Agent（OpenClaw、Claude 等）接上一张隐私支付卡。

比喻实际情况
银行卡更接近附属预付卡：钱先存进资金池，卡只能花分给它的预算，不能透支
主卡和附属卡手机是主卡，Agent 端的 MCP 插件是附属卡。附属卡有自己的密码，主卡看不到；主卡可以冻结附属卡，而且不需要附属卡配合
隐私刷卡时商家只知道“这是一张有效的卡”，不知道持卡人是谁；发卡方（钱包商）也看不到消费明细
POS 机商家用 x402 中间件，加上我们的 facilitator 就能收款

我们的承诺

  • 对外隐私：钱从共享资金池付出，商家只知道“池子里某个已授权的 Agent 付了款”。
  • 可控授权：额度、用途、有效期、子 Agent 层级都写在凭证里，由零知识证明和链上合约强制执行。
  • 主人可审计：每笔交易都被电路强制附上一份只有主人能解开的密文。账单来自链上，不来自 Agent 的自述。
  • 无人持有后门：默认档位里，钱包商不持有任何解密钥。
  • 即插即用：支持 MCP 的 Agent 加一行配置即可接入；x402 商家改一项配置即可收款。

一个用户故事

Alice 在 Claude 里装上 ShadowPass 插件，让研究助理每天最多花 50 积分购买付费数据报告，研究助理再分 10 积分给一个比价子 Agent。某天比价 Agent 被提示注入攻破，偷偷买了一份不相干的报告，而且没有上报。Alice 的手机在本地解密链上新交易后弹出提醒：“子 Agent B 消费 8 积分，未上报。”她按一下 Face ID 吊销 B，研究助理照常工作。整个过程中，钱包商和数据商家都不知道这是 Alice 的 Agent。

02竞品分析

2026 年的黑客松项目、正式产品和研究提案。没有找到同时做到多跳委托、可吊销和主人强制对账的项目。

三类相近方案

A. 隐私 + Agent 支付

  • zk-402（HackMoney 2026，获 ENS 奖）：x402 加一层 ZK 中间件，证明身份承诺有效、金额与报价一致、满足策略。页面未写隐私池、吊销和多跳委托。
  • zkAPI（以太坊基金会，2026-10-01 主网）：存款变私密票据，证明余额足够后换取带额度、会过期的 API key。面向“人付钱给 API”，没有委托树，主人看不到 Agent 的明细。
  • ACTA（ethresear.ch 草案，2026-05）：ERC-8004 之上的匿名凭证。递归委托是开放问题，吊销不在范围内，没有实现。

B. 隐私支付基础设施

  • Unlink（Cannes / NY 2026 赏金）：私密转账 SDK，原语 deposit / transfer / withdraw / execute，Base Sepolia。
  • NY 2026 联合赛道 Private Nanopayments：Dynamic 钱包 + Arc 小额结算 + Unlink 私密转账。隐私来自资金池，Agent 授权仍是钱包商托管策略。
  • Umbra Wallet（Stellar Hacks ZK 第三名）：主打把合规写进密码学，细节未能确认。

C. Agent 授权与策略层（数量最多，不做隐私）

  • Bound（Cannes 2026）：给 Agent 的隔离架构发证书，链上额度、储备、质押审计方、Ledger 联签。
  • AgentPass（Cannes 2026）：ENS 子域名 + World ID 绑定真人 + Ledger 审批。
  • allowance.eth（NY 2026）：策略写进 ENS 文本记录，链上强制。
  • Agent Paymaster（HackMoney 2026）：USDC 策略金库，单笔和每日限额。

评委必问的问题

为什么不用 zkAPI 或 Unlink？

它们回答的是“谁付了钱”。我们回答的是“替谁花、在什么授权范围内花、主人能否查清每一笔”。如果目标赛道有 Unlink 赏金，可以把资金池换成 Unlink，我们只做上面的委托和对账层，前提是先确认 Unlink 的 execute() 能接上我们的 Gate。

为什么不用 ERC-7710 或 session key？

它们能做授权，但委托关系、额度、Agent 地址全部公开。我们同时做到委托方匿名、多跳委托、预算私密和主人强制对账。

商家为什么要接入？

接入成本是在 x402 中间件里多接受一种 scheme、填一个 facilitator 地址。收益是能接到隐私敏感的 Agent 流量，而且收款由合约保证，不会遇到拒付。

03产品形态

四个参与方，两个钱包，三条通道，两把钥，三个机制，三档部署。

参与方：和主流一致，没有新增机构

角色持有做什么看得到
用户手机上的用户钱包：passkey 解锁的根种子，派生出签名钥和查看钥发卡、充值、看账单、吊销、维权自己所有 Agent 的全部花费
Agent（可有子 Agent）电脑上的 Agent 钱包（MCP server）：自己生成的 holder_sk、凭证、预算票据在授权范围内付款，本地生成证明只有自己这一支
商家x402 中间件，收款地址 payTo402 报价、收款、交付“池子里某个已授权 Agent”付了多少
钱包商不持有任何钥托管前端、运行 x402 facilitator（代付 gas）、加密信箱、无内容推送入金金额；facilitator 看到的是商家的请求；信箱里只有密文

验证由链上 Gate 合约完成：证明、状态根、时间、预算 nullifier 全部通过才付款，没有任何一方能插手。

三条通道：大部分时间不需要直连

① 配对（发卡时一次）

MCP server 首次启动生成密钥，在终端显示二维码（Agent 公钥 + 信箱地址）。手机扫码、设额度、Face ID 签发，再把凭证和预算票据秘密用 Agent 公钥加密放进信箱，MCP 去取。

② 收据（Agent 到手机，异步）

每付一笔，MCP 把加密收据放进 Alice 的信箱，用于展示“买了哪份报告”。这条通道不可信也没关系：漏发、少发都会被链上对账发现。

③ 链上（共同的事实来源）

手机直接从 RPC 读事件并解密。吊销完全不需要联系 Agent：手机写上链，Agent 下一个证明就过不了，哪怕它已被攻破、拒绝配合。

Agent 钱包必须跑在用户控制的机器上（自己的电脑、VPS 或 TEE）。证明的输入包含整条委托链，如果托管在钱包商服务器上，钱包商就能看到 Alice 是谁。

两把钥

签名钥查看钥
能力签发、吊销 Agent，分配预算解密“哪一笔是我的哪个 Agent 花的”
存放不落盘。Face ID 时临时派生，用完即丢保存在用户自己的设备上，供后台扫描
泄露后果能动钱只是被看到
给别人永远不给默认不给；企业财务、会计可以单独授权

分开两把钥的主要用途是让异常检测可以常驻后台：后台只放查看钥，签名钥只在 Face ID 时出现。后台被攻破也动不了钱。

三个机制

  1. 共享资金池。所有人的钱混在一个池子里，从池子付款。入金无许可：存多少铸多少预算票据，没有可信铸币方。
  2. 零知识委托证明。Agent 证明“我持有合法委托链，在额度和用途内，没被吊销，预算够”，不暴露链上任何一方。
  3. 给主人的强制密文。电路把整条委托链加密给根凭证里绑定的主人查看公钥。Agent 不能省略或伪造，ElGamal 的密钥隐私性保证密文看不出是给谁的。

三档部署

档位密文谁能看委托链适合
个人版（默认）只有主人密文只有主人个人用户、开发者
企业版只有主人密文，主人是企业根密钥企业财务公司给员工 Agent 发预算
合规版（路线图）主人密文 + 门限合规密文主人；门限多方联合受监管支付。DKG 生成、至少两家独立持有、定期轮换并销毁旧份额

最好所有档位共用一个资金池和 Gate，由同一个电路用参数区分，避免匿名集被拆小。

与 Tornado、Zama 的定位关系

Tornado 没有任何人能解开，用户只能自愿披露；Zama 的全局 FHE 密钥由 13 个 KMS 运营方门限持有。ShadowPass 默认走 Tornado 的思路（无第三方钥匙、用户自查、自愿披露），合规版才采用门限思路。我们隐藏的维度是“Agent 替谁、在什么授权下花钱”，这是两者都没有覆盖的。

MCP server 不直接调用 facilitator：付款凭据交给商家，由商家去 facilitator 结算。

安全模型

  • LLM 永远接触不到密钥。密钥只在 MCP server 进程里。提示注入最多能诱导 Agent 在额度内乱花。
  • 额度、用途、有效期由电路和合约挡住（防）；额度内的乱花由主人手机本地对账发现（发现）；攻击者偷不走密钥，也没法把钱转走。
  • 兼容性：OpenClaw 和 Claude 支持 MCP。其他 Agent 产品需要确认是否支持 MCP；不支持时另外提供 SDK 或 HTTP 接口。

05受理网络：x402 facilitator

卡要能刷，商家得有 POS 机。我们用一个自定义 x402 scheme 解决，估计 6–10 人时，并顶替自建 relayer 和模拟 Escrow。

为什么需要新 scheme

标准 x402 流程：商家返回 402 和付款要求（scheme、网络、金额、payTo、币种）；客户端构造付款凭据放进请求头；商家服务器把凭据交给 facilitator，先 /verify 再 /settle。标准 exact 方案依赖付款人签 EIP-3009 转账授权，而我们的钱从资金池合约付出，合约无法产生这种签名，所以要新增 shadowpass scheme。x402 本身按 scheme 可扩展设计。字段名以开工时的 x402 规范为准。

scheme 设计

  • 付款凭据：{proof, roots, nowTs, action, ct, budget}，即 Gate.execute 的全部参数。
  • action.target 指向新写的 ShadowPayout 合约，它被 Gate 调用后把代币转给 payTo。
  • action.params = abi.encode(payTo, 付款要求哈希)。ctx_hash 把整个 action 绑进证明，所以证明只能付给这个商家的这一次请求，facilitator 无法挪用。
facilitator 接口做什么
/supported声明支持 shadowpass scheme 和 Base Sepolia
/verify金额 ≥ 要求、收款方 = payTo、要求哈希一致、时间新鲜；eth_call 模拟 execute，确认证明有效、nullifier 未用
/settle提交 execute，facilitator 代付 gas，返回交易哈希

三方改动

谁改动
商家照常用 x402 中间件，可接受的 scheme 里加上 shadowpass，填 facilitator 地址
AgentMCP 里的 x402 客户端支持该 scheme，自动生成证明
我们facilitator 服务（约 200–400 行）+ ShadowPayout 合约（几十行）

相对原方案的好处

  • facilitator 兼任 relayer，不再单独做 relayer。
  • 隐私更好：facilitator 被商家服务器调用，看到的是商家的 IP，不是 Agent 的 IP。
  • 信任边界清楚：facilitator 偷不走钱，最多拒绝或拖延结算；商家可以自己运行 facilitator。
  • demo 可以说“任何 x402 商家改一项配置就能收我们的付款”，也能对接 x402 相关的赞助商赛道。

难点

单笔成本：每笔 execute 约 50 万 gas，按 Base 主网常见费用估算每笔约几美分（随 gas 价格波动）。卖几美元的报告可以接受，但零点几美分的按次调用在经济上不成立。规模化路径是会话型 scheme：一个证明给某商家开一个额度会话，期间每次调用只发链下凭据，结束时一次结算。需要改电路或合约，放进路线图。

结算顺序：先 /settle 成功再交付，不采用“先 verify、再交付、再 settle”，避免同一张预算票据被并发使用时商家交付了却收不到钱。代价是每次请求多等一个区块（Base 约 2 秒），加上证明的几秒。

07使用形态与工程决策

网页还是手机、通行密钥怎么用、怎么验证、要不要域名、选哪条测试网。

结论一览

用户钱包
Web PWA，手机优先。手机浏览器打开后添加到主屏幕。原生 App 放到路线图。
Agent 钱包
MCP server，跑在用户自己的电脑上。证明在这里本地生成，和手机扫码配对。
登录
Passkey + WebAuthn PRF，随机根种子由 PRF 包裹，支持多个 passkey 和恢复码。
收款
x402 自定义 scheme + 我们的 facilitator，facilitator 兼任 relayer。
验证
链上 Gate 合约是唯一有约束力的验证者；Agent 提交前预验证；facilitator 用 eth_call 预检；公开一个证明复核页。
部署
注册一个自己的域名。前端放 Vercel 或 Cloudflare Pages；facilitator 和信箱用 serverless 函数。
网络
Base Sepolia（chain id 84532），本地 Anvil 作为现场兜底。

为什么先做网页而不是原生 App

  • 48 小时内一个 PWA 同时覆盖手机和电脑，评委扫码即用，不需要装 App 或走 TestFlight。
  • WebAuthn 和 PRF 在手机浏览器里可用；Face ID 弹窗由系统提供。
  • 异常提醒用 Web Push：钱包商推送一条不含内容的“链上有新交易”，页面被唤醒后在本机解密判断。iOS 需要先添加到主屏幕（16.4 起支持 PWA 推送）。
  • 局限：浏览器后台执行时间有限，iOS 尤其严格。demo 中检测在页面打开时运行，推送负责把人叫回来。常驻后台扫描需要原生 App。

通行密钥怎么用

seed        = 随机 256 bit（只在开通时生成一次）
wrap_i      = AES-GCM( HKDF(PRF(passkey_i, "shadowpass-v1")), seed )   // 每个 passkey 一份
            → 保存在本机，并备份到钱包商（密文，钱包商解不开）
sk_sign     = HKDF(seed, "sign") mod l，且 ≠ 0     // Face ID 时派生，用完清除
sk_view     = HKDF(seed, "view") mod l，且 ≠ 0     // 派生后存入 IndexedDB，供扫描
holder_sk   = Agent 的 MCP server 自己生成，用户只签它的公钥
  • 为什么包裹随机种子，而不直接用 PRF 输出当私钥：每个 passkey 的 PRF 输出不同。直接用的话，换手机或加第二个 passkey 就会得到另一把钥，资金找不回来。包裹种子后，可以给多个 passkey 各存一份包裹，再加一份恢复码包裹。
  • PRF 兼容性：Safari 18 以上（iCloud 钥匙串）和较新的 Chrome（Google 密码管理器）支持。不支持的设备直接提示换设备，不做静默降级。演示设备提前实测。
  • RP ID 绑定域名：passkey 只对创建它的域名有效，域名换掉所有 passkey 都无法使用，所以先定域名再让任何人注册。
  • 研究电路已拒绝 sk = 0（v9.2 修复的 F-2）；派生时同样检查。

怎么验证

层谁做什么约束力
链上Gate + Groth16 Verifier验证证明；检查状态根窗口、时间偏差、ctx_hash 绑定本次 action、nullifier 未使用。失败则整笔回滚唯一有约束力
提交前MCP server用 vk 本地 groth16 verify，失败不提交辅助
结算前Facilitator/verify 检查金额、收款方，eth_call 模拟执行辅助
公开复核任何人证明复核页：输入交易哈希，读取公开输入，用公开 vk 重新验证透明度
主人用户手机解密主人密文，核对 Agent 上报的收据审计

Facilitator 没有验证权和授权权，最多能拒绝结算，换一个即可。证明在用户侧生成是标准模型，安全性依赖 Groth16 的可靠性、电路正确和可信设置未被污染。

部署

  • 域名：注册一个自己的域名作为 passkey 的 RP ID。*.vercel.app 子域名能跑原型，但以后迁移会让所有 passkey 失效。
  • 前端：静态 PWA，部署在 Vercel 或 Cloudflare Pages（WebAuthn 要求 HTTPS，localhost 除外）。
  • Facilitator：serverless 函数 + 一个有测试网 ETH 的热钱包，只调用 Gate.execute，按商家做简单限流。
  • 信箱：serverless 函数 + KV 存储，只存密文，按收件公钥分箱。
  • 证明文件：wasm 和 zkey 随 MCP server 分发，不要求手机下载。
  • 可复现：记录研究仓库 commit c794b29 和 MANIFEST.sha256，新 zkey 记录哈希。

09风险与边界

答辩时主动说明。

项现状生产要求
电路正确性研究电路多轮审计，已修 #53（曲线外公钥）和 F-2（sk=0）。非子群公钥未测；主人密文是新改动重新审计与攻击测试
可信设置只有一次本地 phase-2 贡献，只能用于 demo多方仪式。被污染可以伪造证明，但不能去匿名
单笔成本每笔约 50 万 gas，主网约几美分；不适合零点几美分的按次调用会话型 scheme，一次证明摊到多次调用
付款延迟证明几秒 + 先结算后交付多等一个区块会话型 scheme；更快的证明器
匿名集黑客松时池子里几乎只有自己用户越多越隐私；demo 预置模拟存款并说明
Agent 托管位置demo 在用户笔记本必须是用户控制的机器或 TEE；托管在钱包商处会泄露委托链
元数据商家看得到 Agent 的 IP；委托深度可从密文长度推出网络隐私层、固定深度补齐
吊销生效状态根有宽限窗口，吊销后旧根仍可能短暂有效demo 把窗口设为几秒；生产按风险配置
x402 兼容自定义 scheme 依赖 x402 SDK 的扩展能力，版本差异可能有坑跟进 x402 规范，必要时贡献 scheme 定义
受理网络商家需要接受新 schemefacilitator 开源，商家可自建
剩余中心化点Gate 的 setMethod 由管理员配置商家自助登记，由凭证权限位约束
Passkey 丢失依赖多 passkey 包裹和恢复码社交恢复或硬件备份
