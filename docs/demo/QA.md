# 评委问答：竞品、风险与边界

## 竞品对比

| 方案 | 主要解决什么 | 仍暴露什么 | ShadowPass 的差异 |
|---|---|---|---|
| Coinbase Agentic Wallets、Privy、Turnkey | 托管、策略、审批、Agent 可用性 | 平台通常能看到账户、授权关系和执行；链上仍可能定位到 Smart Account | 钱包商不持钥，商家和链上只看到池内授权分支；主人用查看钥对账 |
| Safe Smart Account + session key | 账户抽象、限额、目标白名单、会话权限 | Smart Account、delegate、权限、calldata 和同账户后续操作通常可关联 | 能力和有效期沿 ZK 委托链逐级收窄；执行主体不直接公开 |
| ERC-7710 delegation | 标准化可编程委托和执行 | delegation 链、delegate、caveat 与执行结果通常公开；隐私取决于实现 | 证明委托链满足约束，不公开完整关系；同样保留可组合的支付接口 |
| x402 `exact` | HTTP 原生按次支付、标准 facilitator | 付款地址与请求可关联 | x402 外层流程不变，替换付款证明为 ShadowPass 池内承诺 |
| 混币器或隐私 L2 | 切断资金来源关联 | 合规、延迟、退出成本和流动性风险更高 | 目标是支付授权隐私，不是混币；不做收益承诺，不引入匿名资金池叙事 |

对照面板中的 ERC-7710 一列是公链观察者的常见暴露模型，不是对某个具体钱包实现的审计结论。某些 Smart Account 可通过新地址、代付或硬件隔离降低关联性，但授权关系和 calldata 仍需要单独设计。

当前版本是协议层演示，不包含钱包 PWA 的 passkey/Touch ID 和 MCP/Claude 操作。它用于验证证明、合约、x402 和 facilitator 链路；完整产品演示在 #44、#47、#48 合并后另做。

## 安全与协议

**为什么采购 Agent 拿不到理财预算？**

根凭证同时有 `PAY` 和 `TREASURY`，但子凭证能力必须是父级子集，预算票据也只签发给对应分支。演示面板会真的用采购凭证申请 TREASURY，`CapSubset` 约束失败，界面显示证明器返回的拒绝信息。

**为什么理财 Agent 不能把钱付给任意商家？**

它只有 `TREASURY`。`TREASURY_SUPPLY` 只允许调用已配置的 `TreasuryAdapter`，Adapter 再限制白名单 ERC-4626 金库。回款 `returnCm` 在存入时已经写进 calldata 和证明上下文。

**如果金库到期收益不够怎么办？**

`TreasuryAdapter` 只在资产覆盖承诺金额或储备能补足容差时生成票据；否则记录 `Shortfall`，不会凭空铸票。演示金库由真实代币预注资，当前部署参数让 24 小时期限获得约 1% 的测试收益。

**伪造证明或篡改金额会怎样？**

公开输入绑定 roots、action、金额、nonce、密文和预算字段。金额、方法、目标或主人密文被改动时，verifier 会拒绝。电路与合约的接受/拒绝用例在各自工单测试中。

**主人能看到什么？**

Alice 用查看钥扫描链上 `OwnerCiphertext` 事件，得到委托链和分支归属，但商家、facilitator 和普通观察者没有查看钥。演示中账本显示“Alice → 管家 → 采购 Agent / 理财 Agent”。

## 隐私边界

**匿名集有多大？**

演示预置 20 个票据层模拟用户，加上 Alice 的票据，初始化后票据集为 25。根凭证身份层仍只有 Alice，身份层匿名集为 1。页面明确标注模拟数据。这个规模只能证明机制可运行，不能证明生产匿名性。

**还暴露哪些元数据？**

金额、时间、目标合约、方法、事件形状、请求频率、facilitator 和商家看到的 IP，以及密文长度对应的委托深度仍可能暴露。ShadowPass 不隐藏这些字段，也不承诺抗流量分析。

**采购和理财真的不可关联吗？**

开通、发卡、划拨、理财 execute 和赎回都通过 facilitator relay 发送，链上执行账户不是 Alice 的 EOA。完整委托链只加密给 Alice。但所有这些动作共享 facilitator 账户，仍可能被按时间和设施聚合；生产部署需要多 facilitator 与流量隔离。

**和混币器有什么不同？**

这里没有匿名资金池、存取混合或收益资产；资金用途由凭证和预算约束。目标是让授权支付不公开主人身份，同时保留主人可审计性。

## 工程风险

| 风险 | 当前处理 | 上线前还需要 |
|---|---|---|
| 电路和合约未经生产审计 | README 和演示页面明确标注原型 | 独立审计、形式化检查、长期漏洞赏金 |
| Groth16 可信设置 | 本地单次 phase-2，仅演示 | 多方 ceremony、公开 transcript 和独立复现 |
| 电路正确性依赖研究基线 | 接受与拒绝用例、manifest 哈希、真实证明 E2E | 扩大负例、模糊测试和跨实现一致性测试 |
| 方法配置中心化 | 部署者配置 `setMethod` | 多签、时间锁、治理和可验证升级流程 |
| 撤销后预算冻结 | 只冻结出问题的分支，避免影响另一支 | 设计父级回收或过期再分配机制 |
| Demo 金库测试收益 | 24 小时期限约 1%，页面不把它当真实收益率 | 生产接入经过审计的 ERC-4626 策略和真实风险参数 |
| 密钥和恢复 | 原型阶段强调本机密钥和查看钥分离 | 通过审计的 passkey PRF、恢复码、设备迁移与社工防护 |
| Facilitator 拒绝服务 | 不掌握资金，最多不代付 | 多 facilitator、fallback 和可观测性 |

## 评审可能追问

**这和普通 session key 白名单有什么区别？**

白名单解决“允许做什么”，ShadowPass 还解决“链上不要把授权人和 Agent 公开串起来”。能力收窄和预算票据进入 ZK 证明，主人密文保留可审计性。

**为什么不直接使用 ERC-4337 paymaster？**

paymaster 可以代付 gas，但不自动隐藏 Smart Account 的授权关系和执行意图。ShadowPass 可作为更上层的支付证明，与账户抽象和 facilitator 组合。

**为什么现在不用 Aave？**

Base Sepolia 上目标资产不是合适的 ERC-4626 接口，演示使用可复现的 MockVault。Adapter 面向 ERC-4626，不把某个借贷协议写死进电路。

**黑客松之后最优先做什么？**

先做外部电路与合约审计、可信设置、生产密钥恢复和撤销后预算回收；再扩大匿名集，最后才考虑更复杂的跨资产和会话型支付。
